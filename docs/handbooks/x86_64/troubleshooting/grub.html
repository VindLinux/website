GRUB

Boot problems are usually easier to isolate by checking each layer separately: firmware, bootloader, partition table, filesystem, and kernel.

1. GRUB — “no such partition”

A common failure looks like this: 

error: kern/disk.c:grub_disk_open:262:no such partition.
Entering rescue mode...
grub rescue>
ls
(hd0) (cd0)

If (hd0) exists but commands such as ls (hd0,gpt1) fail, GRUB can see the disk but cannot access its partition table. This can happen even when the disk and its partitions are completely valid.

2. Check the disk first

Inspect the image from the host before changing anything in the guest: 

qemu-img info disk.qcow2
sudo qemu-nbd --connect=/dev/nbd0 disk.qcow2
sudo fdisk -l /dev/nbd0

A valid GPT with the expected partitions rules out corruption of the disk image as the immediate cause.

3. Check the GRUB modules

GRUB needs the appropriate modules to understand the partition table and filesystem. For a GPT/ext4 system, check that these modules exist: 

ls -l /boot/grub/x86_64-efi/part_gpt.mod
ls -l /boot/grub/x86_64-efi/ext2.mod
ls -l /boot/grub/x86_64-efi/disk.mod

The presence of these files alone does not guarantee that the EFI bootloader was installed with everything it needs.

4. Reinstall GRUB with the required modules

Mount the installed system and EFI partition, then reinstall the EFI loader explicitly: 

grub-install \
    --target=x86_64-efi \
    --efi-directory=/boot/efi \
    --bootloader-id=VindLinux \
    --removable \
    --recheck \
    --modules="part_gpt ext2 disk"

The important part here is explicitly including part_gpt, ext2, and disk. After installation, regenerate the GRUB configuration if necessary: 

grub-mkconfig -o /boot/grub/grub.cfg

5. VirtIO is not necessarily the problem

If the same no such partition error happens with both VirtIO and IDE/SATA disks, the storage bus itself is not the root cause. Test the bootloader before changing the virtual hardware configuration. 

ls
(hd0) (cd0)

ls (hd0,gpt1)
error: kern/disk.c:grub_disk_open:262:no such partition.

In this situation, focus on GRUB's ability to read the disk and partition table rather than changing the filesystem or recreating the disk image.

6. Verify the result

After reinstalling GRUB, boot the system again using the same disk configuration originally intended for the machine. For a VirtIO-backed QEMU disk, the expected result is that GRUB can locate the GPT partitions and continue to the kernel.

The EFI fallback loader should be present at: 

/boot/efi/EFI/BOOT/BOOTX64.EFI

If the system reaches the kernel with the original storage configuration restored, the bootloader installation was the relevant change.
